# staged-task — большая задача → цепочка асинхронных сабагентов

Основная сессия — лёгкий оркестратор: она не выполняет задачу сама, а режет её на этапы, запускает **по одному фоновому сабагенту** на этап (Agent tool, `general-purpose`, `run_in_background: true`), релеит отчёты и вопросы пользователя, будит упавших. Вся рабочая информация живёт на диске, поэтому контекст основной сессии почти не растёт, а результат этапа переживает любое падение доставки.

Не используй для мелких задач (проще сделать самому) и для задач, требующих плотного интерактива с пользователем на каждом шаге.

## Схема работы

1. **Приём**: разбить задачу (или оформить готовое разбиение) → `PLAN.md` → показать заголовки этапов юзеру (информативно, ответа не ждать) → старт сразу. Ожидание — только на блокирующих вопросах (контракты 1–2) и красных линиях, НЕ на подтверждении плана.
2. **Цикл**: короткий промпт → фоновый запуск → записать agentId → **конец хода**. Уведомление о завершении придёт само. Маркер «ОТЧЁТ» → вывести и сразу запустить следующий этап. Маркер «ВОПРОС» → вывести вопрос, ждать ответа пользователя, разбудить агента ответом.
3. **Аварии**: «разбуди An» → проверить статус → SendMessage по сохранённому agentId.

## Артефакты рана — `<cwd>/.staged/<slug>/`

Создаются оркестратором до первого запуска. `<slug>` — короткий kebab-case от сути задачи, `<cwd>` — корень рабочего каталога сессии. Пути в промптах всегда абсолютные.

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `PLAN.md` | только оркестратор (сабагентам запрещено) | глобальный контекст, контракты сабагента, инструкции этапов, таблица статусов с agentId |
| `NOTES.md` | все, append-only | живые заметки: конвенции, грабли, решения; создаётся пустым на старте |
| `reports/A1.md`, `A2.md`… | сабагент этапа | полный отчёт этапа + блок «⇒ Для следующего этапа»; дописывается по ходу работы и обязательно — до возврата |
| `ORCH_PLAYBOOK.md` | оркестратор, из шаблона `templates/ORCH_PLAYBOOK.md` | runbook: правила, цикл этапа, промпты запуска, роли агентов, схема `stage/A<n>.json`. Нужен для длинных задач (см. «Контекстный бюджет оркестратора») |
| `tools/` | субагент-инструментальщик (один раз на трек) | готовые команды оркестратора: скрипт строк статусов PLAN, механическая сверка этапа; описаны в `tools/README.md` |

## Приём задачи

- **Задача не разбита**: разбей сам. Этап = самодостаточный кусок ~10–40 минут работы сабагента с проверяемым критерием готовности (крупнее — много теряем при падении; мельче — накладные расходы на запуск). Этапы слабо связаны: следующий зависит от результатов предыдущего, но не от его внутренностей. Запиши `PLAN.md` по заготовке ниже. Если при разбиении возникли блокирующие развилки (архитектурное решение, дилемма, дорогой откат) — задай их пользователю ДО запуска: блокирующий вопрос — единственная точка ожидания, подтверждение плана — НЕТ. Затем покажи **только список заголовков** этапов (A1…An) — информативно — и стартуй конвейер.
- **Задача уже разбита**: оформи готовый список этапов в `PLAN.md` как есть, не перепланируй. Неясности — блокирующие вопросы пользователю до запуска (не подтверждение плана).

### Заготовка PLAN.md (копируй и заполняй)

```markdown
# Задача «<slug>» — <краткое название>

- Создан: <дата>
- Каталог рана: <абс>/.staged/<slug>/

## Глобальный контекст (читает каждый сабагент)

- Проект: <1–2 предложения, ключевые пути>
- Конвенции: <ветки, стиль, как запускать тесты/сборку>
- Как проверять сделанное: <команды>
- Красные линии: <чего не делать>

## Контракты сабагента (обязательны, копируй дословно из скилла)

## Этапы

### A1 — <заголовок>
- Цель: <одним предложением>
- Вход: <что прочитать сверх обязательного: файлы, issues>
- Сделать: <список>
- Критерий готовности: <проверяемое условие>

### A2 — …

## Статусы

| Этап | Статус | agentId | Запущен | Завершён |
|---|---|---|---|---|
| A1 | pending | — | — | — |
```

Статусы: `pending` → `running` (agentId, время) → `done` | `question` (агент остановлен, ждёт ответа пользователя) | `failed`.

## Запуск этапа

Промпт — одна строка смысла, всё остальное агент читает с диска:

```
Этап A2 задачи «<slug>». Прочитай по порядку:
1) <абс>/.staged/<slug>/PLAN.md — разделы «Глобальный контекст», «Контракты сабагента» и секция «A2»
2) <абс>/.staged/<slug>/NOTES.md
3) <абс>/.staged/<slug>/reports/A1.md — только блок «⇒ Для следующего этапа»
Затем выполни этап по контракту.
```

(для A1 пункт 3 отсутствует)

В ране с runbook цикл ведётся по `ORCH_PLAYBOOK.md`, а в ход пишется одна готовая команда (см. «Контекстный бюджет оркестратора»).

Действия оркестратора:

1. `Agent` с `subagent_type="general-purpose"`, `run_in_background=true` и этим промптом.
2. **Сразу** записать agentId в таблицу статусов `PLAN.md` (`running`, время запуска; в ране с runbook — готовой командой скрипта раны) и убедиться, что запущена автоматика мониторинга из раздела «Контекст агента у лимита» (создать, если её нет).
3. Одна строка пользователю: «▶ A2 запущен в фоне. Если заметишь, что встал — скажи „разбуди A2“. Другие задачи мне можно задавать как обычно.» agentId — внутренний идентификатор: в чат его не выводи, единственное место хранения — таблица статусов PLAN.md, пользователь обращается к агенту по номеру этапа.
4. **Завершить ход.** Не поллить статус, не подглядывать в работу агента, не делать её за него. Уведомление о завершении придёт само и разбудит тебя.

## Уведомление о завершении: смотри маркер первой строки

Если уведомление пришло усечённым — возьми полный вывод через `TaskOutput` или прочитай `reports/An.md`.

**«ОТЧЁТ (этап An)»**:
- выведи отчёт пользователю как есть (он уже краткий, ≤25 строк) + ссылку на `reports/An.md`;
- отметь `done` в `PLAN.md`;
- если есть следующий этап — **сразу** запусти его тем же шаблоном, не ожидая пользователя;
- если это был последний — финальное резюме всей задачи (5–10 строк из отчётов) + где лежат `PLAN.md`/`NOTES.md`.

**«ВОПРОС (этап An): <текст>»** — это не отчёт, следующий этап НЕ запускается:
1. Выведи вопрос дословно, укажи этап.
2. **Заверши ход и жди ответа пользователя.**
3. После ответа: `SendMessage(agentId, "Ответ пользователя (дословно): «<ответ>». Продолжай этап A2.")` — агент пробудится с сохранённым контекстом. Цикл ВОПРОС→ответ может повторяться. Если у вопроса 2–4 чётких варианта, можно использовать AskUserQuestion, но ответ агенту пересылай дословно.

Сообщение без маркера трактуется как отчёт — выведи как есть.

## Контекст агента у лимита: автомониторинг → суммаризация → перезапуск

Окно сабагента — **500 000 токенов** (не 1 000 000, как у основной сессии). Порог отправки сообщения — **250 000 абсолютных токенов**: `zctx -s <agentId> --limit 500000 --warn-at 250000`, действие при `status=warn` (≥250k) или `stop` (≥450k). Автосуммаризация платформы сработает сама у реального предела окна (~500k) — она не настраивается и не отключается; наш триггер на 250k должен успеть раньше.

### Автоматика мониторинга (каждые 7 минут)

Жизненный цикл автоматики строго привязан к сабагентам:

- **Запуск этапа** (каждый `Agent` с `run_in_background: true`): если автоматики ещё нет — `CronCreate` с интервалом 7 минут (`intervalUnit=minute`, `interval=7`), title «Мониторинг контекста staged-task <slug>», prompt (подставь slug и абсолютный путь):

  > Проверь контекст бегущих этапов задачи «<slug>»: прочитай <абс>/.staged/<slug>/PLAN.md. Для каждого этапа со статусом running выполни `zctx -s <agentId> --limit 500000 --warn-at 250000` (транскрипт появляется в ~/.zcode/cli/rollout/ после первого вызова модели агентом; `session not found` = только стартовал, всё в порядке). При status=warn или stop — отправь этому агенту SendMessage с командой суммаризации и остановки из раздела «Контекст агента у лимита» скилла staged-task, затем обработай передачу этапа по этому же разделу. Если все running-этапы в порядке — ничего не делай и пользователю не пиши. Если running-этапов в PLAN.md нет — одной строкой напомни пользователю, что автоматика мониторинга больше не нужна (её id записан в PLAN.md; сама её не удаляй и не создавай новую). Если PLAN.md уже читался в текущем окне сессии и таблица статусов с тех пор не менялась — повторно не читай, достаточно zctx-проверки по known-running agentId (текущий список — из последнего редактирования/чтения таблицы статусов).

  id автоматики запиши в PLAN.md отдельной строкой под таблицей статусов: `Автоматика мониторинга: <id>`.

- **Любая остановка сабагента** — успешное завершение этапа (ОТЧЁТ → done), вопрос пользователю (ВОПРОС → question), падение, передача по лимиту контекста без немедленного перезапуска — после обработки сверься с PLAN.md: если running-этапов не осталось, `CronDelete(<id>)` и удали строку автоматики из PLAN.md. Передача по лимиту с немедленным перезапуском этапа автоматику НЕ останавливает — новый агент снова running, мониторинг продолжает следить уже за ним.

Ограничение платформы: срабатывание автоматики не может удалить саму себя, поэтому удаление всегда происходит в обычном ходе обработки остановки этапа; подстраховка — напоминание из промпта при пустых running. Скорость роста: за 7 минут агент может добавить десятки тысяч токенов (большие чтения файлов), поэтому warn может быть перескочен между проверками — при stop действуй так же, как при warn (команда суммаризации может прийти уже после автосуммаризации ZCode; тогда попроси агента дописать в отчёт пост-компактный статус и перезапусти этап).

Дополнительно к автоматике, при любом собственном пробуждении (сообщение пользователя, уведомление, «что с этапом?») прогоняй ту же проверку попутно — так порог ловится раньше таймера. Без `-s` zctx не вызывай: при работающем агенте дефолтный замер покажет его файл вместо основной сессии.

### Команда суммаризации (кооперативная остановка)

При warn/stop SendMessage по agentId:

> Твой контекст близок к лимиту. Прекрати выполнение и допиши в <абс>/.staged/<slug>/reports/A<n>.md самодостаточную суммаризацию прогресса: что сделано (пути, команды, решения), что в работе в момент остановки, что осталось до критерия готовности, грабли. Отчёт будет передан новому агенту вместе с исходной инструкцией этапа — пиши так, чтобы он мог продолжить с этого места; саму инструкцию этапа в отчёт не дублируй, она придёт новому агенту дословно той же, что получил ты. Закончив, верни краткий отчёт ≤20 строк, первая строка — «ОТЧЁТ (этап A<n>): контекст исчерпан, суммаризация записана».

### Обработка передачи этапа

Отчёт с первой строкой «ОТЧЁТ (этап A<n>): контекст исчерпан, суммаризация записана» — особый случай, текст отчёта в основную сессию НЕ выводи (контекст оркестратора не раздуваем). Действия:

1. Одна строка пользователю: «A<n> остановлен по лимиту контекста, суммаризация: <абс>/.staged/<slug>/reports/A<n>.md — передаю этап новому агенту.»
2. Запусти нового сабагента на тот же этап: **стандартный промпт этапа дословно** (тот же, что получил предшественник) + приписка: «Этап A<n> начат ранее другим агентом и остановлен по лимиту контекста. Его самодостаточная суммаризация: <абс>/.staged/<slug>/reports/A<n>.md — прочитай целиком и продолжай с этого места, сделанное не переделывай.»
3. agentId в таблице статусов замени на нового (этап остаётся running), в NOTES.md строка `[orch] A<n> перезапущен по лимиту контекста`. Автоматику мониторинга не трогай — следит за новым агентом.

Агент уже ушёл в stop / не отвечает / упал — суммаризации не жди, перезапускай по правилу «agentId мёртв» из следующего раздела.

## Контракты сабагента (копируй в PLAN.md дословно)

1. Сначала попробуй решить вопрос сам по PLAN.md / NOTES.md / коду. Спрашивай, только если выбор блокирующий и неверный вариант дорого откатывать.
2. Хочешь спросить — сначала допиши в `reports/A<n>.md` секцию «## Статус на момент вопроса» (что сделано / что осталось / что блокирует), затем заверши ход сообщением, первая строка — «ВОПРОС (этап A<n>): <текст>».
3. Перед завершением работы запиши полный отчёт в `reports/A<n>.md`, закончи его блоком «⇒ Для следующего этапа» (5–7 пунктов: что изменилось, где, грабли). Пиши на диск ДО возврата — отчёт должен пережить падение.
4. Верни финальное сообщение ≤25 строк, первая строка — «ОТЧЁТ (этап A<n>)»: статус, что сделано, ключевые файлы, путь к полному отчёту. Полный отчёт живёт только в файле раны `reports/A<n>.md` — в сообщение его не дублируй.
5. `PLAN.md` и таблицу статусов не трогай — это оркестратор. `NOTES.md` можно дополнять (append, каждая запись с префиксом `[A<n>]`).

## Аварии и пробуждение

Пользователь: «A3 встал / завис / разбуди A3»:
1. `TaskOutput(task_id, block=false)` по сохранённому id. Ещё работает — так и скажи, результат не выдумывай. Завершился или упал — дальше.
2. `SendMessage(agentId, "Продолжай этап A3 с места остановки. Если уже завершён — запиши отчёт в reports/A3.md и верни краткий отчёт (первая строка «ОТЧЁТ»).")` — контекст агента сохраняется, с нуля работа не перезапускается.

agentId мёртв (перезапуск сессии и т.п.) — запусти нового сабагента на этот же этап со стандартным промптом и припиской: «Этап мог быть начат ранее: сверься с reports/A<n>.md (включая „Статус на момент вопроса“) и фактическим состоянием файлов/git — дозаверши, сделанное не переделывай.»

**Продолжение в новой сессии** («продолжи задачу <slug>» / «продолжи этапы»): прочитай `PLAN.md`, возьми первый этап не `done` и продолжай цикл. Slug не назван — найди последний `.staged/*/PLAN.md` с незавершёнными этапами. В ране есть `ORCH_PLAYBOOK.md` — начинай с него (правила, цикл, промпты) + таблицы статусов `PLAN.md`.

## Правила экономии токенов (оркестратор)

- Не читай в основной сессии исходники и файлы задачи — вся информация из отчётов и PLAN.md.
- Не пересказывай PLAN.md в чат: подтверждение — только заголовки этапов; отчёты — как есть.
- После запуска агента сразу заканчивай ход; никакого поллинга TaskOutput.
- Пока этап выполняется, другие запросы пользователя выполняй как обычно — фоновый агент не блокирует сессию.
- «Что с этапом?» → `TaskOutput(block=false)` и короткий ответ без домыслов.
- Параллельный запуск нескольких этапов — только по явной просьбе пользователя; по умолчанию строго по одному.

### Контекстный бюджет оркестратора

Зачем: замер 24.11.2026 — за 35 минут окно основной сессии выросло 79k → 306k токенов; из них ~183k — собственные ответы модели (скрипт ревью писался и ~10 раз патчился прямо в основной сессии), ~44k — выводы инструментов. Правила выше этого не запрещают — запрещает и меряет этот раздел.

1. **Ноль кода в основной сессии.** Инструменты (скрипт строк статусов PLAN, механическая сверка этапа) — субагент-инструментальщик, один раз на трек, складывает в `tools/` раны. Отладка и разбор проблем — субагент-следователь (вердикт ≤30 строк). Оркестратор только запускает готовые команды.
2. **Выводы команд — в файл**, в контекст — хвост: `cmd > файл 2>&1; tail -n 40 файл | cut -c1-200`.
3. **Диффы в основной сессии не читать, если есть механическая сверка** (`tools/` раны; в контекст — только её итог). Слайсы — исключение, и лучше через субагента.
4. **Записи NOTES ≤700 символов** со ссылками на файлы; строки PLAN — скриптом раны, не правкой руками.
5. **Промпты и цикл этапа — в `ORCH_PLAYBOOK.md` раны** (runbook; шаблон — `templates/ORCH_PLAYBOOK.md` репозитория скилла, при симлинк-установке — `~/.agents/skills/staged-task/../../templates/ORCH_PLAYBOOK.md`). Создавать копированием шаблона и заполнением заглушек; агентам передаются пути к файлам раны, а не тексты.
6. **После компакции** состояние восстанавливать из `ORCH_PLAYBOOK.md` + таблицы статусов `PLAN.md` раны, а не из саммари.
7. **Замер на границах этапов:** `zctx --main --delta 20` (своя сессия, без `-s`). «Свои ответы» ≥60% или рост за этап ≥40k — правило нарушено: оформить эту работу в задание субагенту (инструментальщик / следователь), а не продолжать руками. `requests` меньше 20 — окно неполное (транскрипт сессии обрезан), делать выводы по нему осторожно.
8. **Рассуждения короткие:** план — в промпте субагенту, не в размышлениях.

### Ревью-протокол оркестратора (трек-режим; большие артефакты)

- Дифф PR руками не читай, если есть механическая сверка (`tools/` раны): её вывод — в файл, в контекст — итог (`problems = <число>`); `problems > 0` — разбирать следователю, не оркестратору.
- Слайсы — исключение (сверки нет): дифф перед чтением оцени размером (`wc -l`); >400 строк — читай слайсами по 300–400 строк, и лучше через субагента; дубликатов в контексте не сохраняй.
- Doc-PR >800 строк (планы фаз, финальные доки): построчное чтение не обязательно — читай шапку-статус, оглавление/структуру разделов и якорные секции (гейты, красные линии, стоп-точки), полноту проверяй структурно (`wc -l`, grep-оглавление заголовков). Построчное чтение целиком — только для код-PR без механической сверки (исключение из правила о диффах).
- `reports/A<n>.md` читай по якорям: шапка-статус → таблица гейтов → блок «⇒ Для следующего этапа». Полное чтение — только при расхождении якорей с независимыми сверками.
- Строки статусов PLAN.md раны — скриптом раны (одна команда на границу этапа); без скрипта — компактные, ≤3 строки на этап: итог + PR/merge-sha + главное отклонение. Детали ревью и верификаций — только в отчётах/NOTES, не в PLAN.md.
- Срабатывания мониторинга при [ok] — молча, без резюме в чат и без перечитывания PLAN.md (см. шаблон промпта автоматики).
