# track-task — трек: playbook фаз → план фазы → конвейер этапов

Три уровня:

- **Трек** (большая задача) = фазы; живёт в playbook-доке (формат ниже). Режим 1 создаёт playbook, Режим 2 ведёт фазы.
- **Фаза** = много мелких этапов; живёт в плане фазы `<область>/PHASE<N>_PLAN.md` (пишет фоновый сабагент-планировщик).
- **Этап** = один фоновый сабагент = один PR/коммит; конвейер этапов всегда исполняет скилл **staged-task**.

Основная сессия — лёгкий оркестратор: не режет трек и фазы сама, не исполняет этапы. Работает **в паре со staged-task** (`~/.agents/skills/staged-task/SKILL.md`; каталог не переименовывать): фазовый уровень (приём, планировщики, ревью, статусы, закрытие) — этот скилл; этапный (фоновый запуск по одному, конец хода, маркеры «ОТЧЁТ»/«ВОПРОС», автомониторинг контекста, аварии и пробуждение, экономия токенов) — дословно по SKILL.md staged-task, при Шаге 2 конвейера прочитай его и следуй ему; контракты сабагента копируются в PLAN.md раны из staged-task, не пересочиняются.

**Автономность (правило юзера).** Скилл действует самостоятельно и НЕ ждёт подтверждений юзера на планы/разбивки: заголовки фаз и этапов показываются юзеру информативно (строка на фазу/этап), после ревью оркестратора работа продолжается сама. Останавливаться — только на: блокирующих вопросах по проекту (ВОПРОС сабагента: архитектурные решения, дилеммы, дорогие в откате развилки), операциях с продом/деплоем (красные линии области), конце диапазона/трека, отсутствии входов.

**Мониторинг контекста — на КАЖДЫЙ фоновый запуск.** Архитектор трека и планировщики фаз — такие же фоновые агенты, как этапы: сразу после Agent-запуска создай/проверь автоматику zctx-мониторинга раны по контракту staged-task (раздел «Автоматика мониторинга»: CronCreate раз в 7 минут, `zctx -s <agentId> --limit 500000 --warn-at 250000`; при warn/stop — команда суммаризации и передача роли новому агенту с суммаризацией). Автоматика раны трека следит за архитектором/планировщиком (agentId — в PLAN.md раны трека); конвейер этапов в ране фазы — своя автоматика (по staged-task). Когда бегущих агентов раны не осталось — CronDelete (жизненный цикл staged-task); id автоматики — только в PLAN.md, не в чате.

Не использовать: задача уже размечена на этапы → сразу staged-task; задача мала (фаз и этапов не нужно) → сделать самому.

## Схема

- **Режим 1 — создать playbook**: большая задача не размечена → архитектор трека → черновик playbook → ревью оркестратора → фиксация doc-PR (заголовки фаз — юзеру информативно, без ожидания). Старт исполнения — отдельной командой юзера.
- **Режим 2 — исполнить фазу**: playbook есть → планировщик фазы → план фазы (этапы P1…Pn) → ревью → конвейер staged-task (A<i> = P<i>) → закрытие фазы (заголовки P1…Pn — юзеру информативно, без ожидания). Запуск: «исполни фазу N» (одна фаза, дальше стоп) или «исполни фазы A–B» / «весь трек» — **авто-диапазон**: после закрытия фазы оркестратор сам переходит к следующей фазе диапазона (условия стопа — «Закрытие фазы»).
- **Сопровождение**: «продолжи трек/фазу», «что с фазой», «разбуди планировщика/этап».

## Режим 1 — создать playbook

Вход: формулировка большой задачи + область (репо/каталоги) + ограничения юзера. Если задача не тянет на несколько фаз — предложи staged-task или сделай сам.

1. Рана трека `<cwd>/.staged/<slug>/`: `PLAN.md` (slug трека, путь playbook, agentId архитектора в разделе «Трек»), пустой `NOTES.md`. agentId — только там, не в чате.
2. Фоновый сабагент-архитектор (`general-purpose`, `run_in_background`), промпт одной строкой смысла:

```
Архитектор трека «<slug>»: <задача дословно>. Область: <пути>. Прочитай <рана>/reports/architect.md (если есть — продолжи).
Изучи область (код, при необходимости — замеры/инвентарь: размеры, зависимости, хранилища, тесты) и предложи разметку трека на фазы.
Напиши черновик playbook <абс>/<путь playbook> по заготовке из скилла track-task (диктую дословно ниже) + протокол решений
в <рана>/reports/architect.md (почему такие фазы/границы, чем заполнял правила). Код не трогай. Верни ≤20 строк, первая строка
«ПЛАН (трек)»: заголовки фаз 0…n по строке, путь к playbook.
```

(Заготовку playbook включай в промпт дословно — архитектор не читает этот скилл.) Сразу после запуска — автоматика zctx-мониторинга раны (см. «Мониторинг контекста» выше).

Контракты архитектора = контракты планировщика фазы (см. Режим 2): пишет только playbook + `reports/architect.md`; код не трогает; вопрос — сначала «Статус на момент вопроса» в протокол, затем ход с первой строкой «ВОПРОС (архитектор трека): …»; протокол на диск ДО возврата; отчёт ≤20 строк с маркером «ПЛАН (трек)».

3. Ревью оркестратора (только по черновику, исходники не читать):
   - фазы крупные и самостоятельные: каждая завершается консистентным состоянием (зелёный сьют/сборка, работающий сервис, задокументированность);
   - порядок фаз фиксированный и обоснованный (строка «почему здесь» у каждой);
   - **сквозные правила отделены от фаз**: всё, что верно для любой фазы (гейты PR, паритет, красные линии), — в раздел правил, а не в тексты фаз;
   - красные линии собраны; опора на факты (замеры), не прикидки.
   Замечания → SendMessage архитектору, правит тот же doc-PR.
4. Юзеру — только заголовки фаз (строка на фазу), информативно: ответа НЕ ждать. Правки, если юзер даст их позже, — снова архитектору (SendMessage), дожидаться их по умолчанию не нужно.
5. Фиксация playbook сразу после ревью: в git-репо — ветка docs → PR → мерж; вне репо — файл по оговорённому с юзером пути. Статус «утверждён», дата, в шапке.
6. Рана трека остаётся: в неё же лягут раны фаз (см. ниже). Фазы НЕ стартуют сами — старт отдельной командой (она же может сразу задать авто-диапазон: «исполни весь трек»).

### Заготовка playbook (передаётся архитектору дословно)

```markdown
# PLAYBOOK «<slug>» — <название трека>
- Создан: <дата>. Статус: черновик | утверждён | в работе | ЗАВЕРШЁН <дата> (итог: <sha/PR-ы>)
- Область: <пути>. Контекст трека: <2–4 предложения>

## 1. Фазы (фиксированный порядок)

### Фаза 0 — <название>
- Цель: <одним предложением>
- Вход: <что должно существовать до старта>
- Сделать: <список>
- Гейты: <проверки>
- Критерий готовности: <проверяемое условие>
- Почему здесь: <строка обоснования порядка>

### Фаза 1 — …

## 2. Сквозные правила (действуют на КАЖДОЙ фазе, у каждого этапа)
<нумерованные П1…Пn: паритет/неизменность поведения, обращение с тестами, git-процесс,
гейты каждого PR, запреты «долга», генерированный код, журнал багов, финал трека, красные линии>

## 3. Карта применимости и статусы фаз

| Область | Фазы | Статус | Примечание |
|---|---|---|---|
| <…> | 0–5 (3 — если <условие>) | pending | <…> |

## 4. Definition of Done (признаки завершённости трека для области)
- [ ] <…>
```

## Режим 2 — исполнить фазу

1. **Приём**: playbook-док + номер/название фазы + область. Проверить: предыдущие фазы закрыты (карта/статусы playbook), входы фазы существуют (например, замер Фазы 0 для планировщика Фазы 1+). Если задан диапазон («фазы A–B»/«весь трек») — зафиксируй его строкой в PLAN.md раны фазы («Авто-диапазон фаз: A–B»): он должен пережить перезапуск сессии. План фазы уже существует и актуален → Шаг 1 пропустить, сразу ревью и Шаг 2. Отметь фазу «в работе» в playbook.
2. **Шаг 1 — планировщик фазы** (фоновый сабагент). Рана фазы: `<cwd>/.staged/<slug>-phase<N>/` (PLAN.md раны с agentId планировщика в разделе «Фаза», NOTES.md, reports/) — создаётся до запуска. Промпт:

```
Планировщик фазы N «<название>» трека «<slug>». Прочитай по порядку:
1) <абс>/<playbook> ЦЕЛИКОМ — фаза N, порядок фаз, правила/красные линии
2) входы фазы: <замер/инвентарь/контекст — абсолютные пути>
3) <рана фазы>/reports/planner.md — если есть, продолжи с этого места
Затем: разбей фазу на мелкие этапы и напиши <абс>/<область>/PHASE<N>_PLAN.md по заготовке (диктую дословно ниже).
Затем ветка docs → commit → push → PR (doc), без мержа. Этапы НЕ исполняй. Верни ≤20 строк, первая строка
«ПЛАН (фаза N)»: заголовки P1…Pn по строке, путь к плану, номер PR.
```

Сразу после запуска планировщика — автоматика zctx-мониторинга раны (см. «Мониторинг контекста» выше).

Контракты планировщика:
1. Пишет только `PHASE<N>_PLAN.md` + `reports/planner.md` + doc-PR. Код и тесты не трогает (читать можно).
2. Сначала попробуй решить вопрос сам по playbook/входам/коду; спрашивай, только если развилка блокирующая. Вопрос — сначала секция «Статус на момент вопроса» в `reports/planner.md`, затем ход с первой строкой «ВОПРОС (планировщик фазы N): …».
3. Полный протокол разбивки (что взял из входов, почему такие границы) пиши в `reports/planner.md` ДО возврата.
4. Отчёт ≤20 строк, первая строка «ПЛАН (фаза N)».

### Заготовка плана фазы (передаётся планировщику дословно)

```markdown
# PHASE<N>_PLAN — <область>, фаза N «<название>»
- Создан: <дата>. Playbook: <путь>. Статус: черновик | утверждён | ВЫПОЛНЕНА <дата> (PR-ы <диапазон>, main <sha>)

## Глобальный контекст (читает каждый сабагент-исполнитель)
- Проект: <1–2 предложения, ключевые пути>
- Конвенции: <ветки, сборка/тесты — команды дословно>
- Как проверять сделанное: <команды>
- Красные линии: <копия из playbook ДОСЛОВНО>

## Этапы

### P1 — <заголовок>
- Цель: <одним предложением>
- Вход: <что прочитать сверх глобального контекста>
- Сделать: <список>
- Гейты: <проверки, которые обязаны пройти>
- Критерий готовности: <проверяемое условие>

### P2 — …
### P<последний> — финал фазы: <сводный прогон, доки, (если фаза требует) деплой>

## Замер / инвентарь <если фаза его требует: таблицы фактов, на которые опираются этапы>
```

Требования к разбивке (обязательны планировщику, ревьюит оркестратор):
- **один этап = один PR**: компиляция + полный сьют укладываются в разумное время; лучше больше мелких этапов, чем один огромный;
- **каждый этап самодостаточен**: промпт запуска исчерпывается «изучи PHASE<N>_PLAN.md целиком, твой этап P<i>, действуй»;
- этапы независимы насколько возможно; завершающий этап-«финал фазы» обязателен;
- опора на факты из входов (замер/инвентарь), не на прикидки; ничего из красных линий.

### Ревью плана фазы

1. Оркестратор читает план и проходит чек-лист требований; сверяет, что «Красные линии» — дословная копия из playbook. Замечания → SendMessage планировщику (правит тот же PR; конвейер ждёт внесения правок, юзера — нет).
2. Юзеру — заголовки P1…Pn (строка на этап), информативно: ответа НЕ ждать.
3. Сразу после ревью (замечаний нет или внесены): смёржить doc-PR плана, обновить main (для git-областей). Конвейер стартует от свежего main с планом в main — юзера не ждёт.

### Шаг 2 — конвейер этапов

Прочитай скилл **staged-task** и следуй ему дословно. Специфика фазового уровня:

- PLAN.md раны фазы: в «Глобальном контексте» вместо пересказа правил — указание читать план фазы целиком + копия красных линий; «Контракты сабагента» — дословная копия из скилла staged-task; этапы A<i> = P<i> с теми же заголовками; таблица статусов — по скиллу.
- Промпт этапа:

```
Этап A<i> (= P<i>) фазы N «<slug>». Прочитай по порядку:
1) <абс>/<область>/PHASE<N>_PLAN.md — ЦЕЛИКОМ (глобальный контекст, правила, все этапы; исполняешь P<i>)
2) <рана фазы>/NOTES.md
3) <рана фазы>/reports/A<пред>.md — только блок «⇒ Для следующего этапа»
Затем выполни этап по контракту.
```

- Старт-стоп прода/деплой — только если это часть этапа (обычно финал-этап) и строго по правилам playbook.

### Закрытие фазы

После `done` последнего этапа (финал-этап включает сводный прогон и доки):
1. Один doc-PR на оба статуса: шапка плана фазы → «ВЫПОЛНЕНА <дата>: PR-ы <диапазон>, main <sha>, <строка итога>»; карта/статусы в playbook → фаза done.
2. Финальное резюме юзору (5–10 строк): итог фазы, PR-ы, итоговый main, где лежат план фазы и рана (PLAN.md/NOTES.md).
3. Следующая фаза:
   - **без авто-диапазона** — только по команде юзера;
   - **с авто-диапазоном** («фазы A–B»/«весь трек») — сразу переходи к приёму следующей фазы диапазона (запуск её планировщика) без ожидания юзера; **стоп с вопросом юзеру** только если: следующая фаза требует деплоя/старт-стопа прода; следующая фаза вне диапазона (диапазон/трек исчерпан); у следующей фазы нет готовых входов; в playbook следующая фаза помечена невыполнимой для этой области (карта применимости).
   Заголовки этапов каждой фазы показываются юзеру информативно — подтверждений разбивки нет. Ответ юзера на ВОПРОС сабагента диапазон не прерывает — после ответа конвейер фаз продолжается.

## Сопровождение и продолжение

- «Продолжи трек <slug>» / «продолжи фазы»: playbook — источник истины; если в ране фазы зафиксирован авто-диапазон — продолжай его выполнение; иначе первая фаза не-done с готовыми входами → предложить её старт (Режим 2). Slug не назван — последний `.staged/*-phase*/` или playbook с незакрытыми фазами.
- «Продолжи фазу N <slug>»: рана `.staged/<slug>-phase<N>/`; по её PLAN.md определи уровень (планировщик / этапы A<i>) и действуй; рана и план фазы — источник истины.
- «Что с фазой?» → короткий статус из PLAN.md раны (планировщик/этап running, какие done) без домыслов; для этапа — `TaskOutput(block=false)` по staged-task.

## Аварии

- Планировщик (фазы или трека) встал/упал («разбуди планировщика») — по образцу staged-task: `TaskOutput(block=false)` по agentId из PLAN.md раны; работает — так и скажи; завершился/упал → `SendMessage` «Продолжай с места остановки…»; мёртв → новый запуск тем же промптом с припиской «сверься с reports/<planner|architect>.md и фактическим состоянием файлов/git, сделанное не переделывай».
- Конвейер этапов — правила аварий staged-task без изменений.

## Экономия токенов (оркестратор)

- Не читай исходники и playbook целиком в основной сессии — входы передаются сабагентам путями; ревью черновиков — только по самим черновикам.
- Не пересказывай playbook/план фазы в чат: подтверждение — только заголовки фаз/этапов.
- После любого фонового запуска сразу заканчивай ход; никакого поллинга.
- Пока планировщики/этапы работают, другие запросы юзера выполняй как обычно.
