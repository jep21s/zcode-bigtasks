# ORCH_PLAYBOOK — runbook оркестратора трека «<slug>»

Действует с <дата>. Цель: основная сессия тратит на этап ≤ ~40k токенов — только готовые команды и сводки ≤ 40 строк.
Рана: `<абс>/.staged/<slug>/`. Скрипты: `tools/` раны (`tools/README.md`). Параметры этапа: `stage/A<n>.json` (схема в конце).
Статусы: таблица `PLAN.md` раны; строки пишет только скрипт `tools/book`. agentId — только в PLAN.md, не в чат.
Новое окно / после компакции: состояние — из этого файла + таблицы статусов PLAN.md, не из саммари.

## Правила (обязательны)

1. Ноль кода в основной сессии: новый инструмент, отладка, разбор проблемы — субагенту (инструментальщик / следователь). Оркестратор запускает готовые команды.
2. Вывод любой команды — в файл (`> файл 2>&1`), в контекст — `tail -n 40 файл | cut -c1-200`.
3. Диффы не читать, если есть механическая сверка; слайсы — исключение, лучше через субагента.
4. Записи NOTES ≤ 700 символов со ссылками на файлы; строки PLAN — скриптом.
5. Рассуждения короткие; сообщения юзеру — итог + отклонения, без пересказа.
6. На границах этапов — `zctx --main --delta 20`: «свои ответы» ≥ 60% или рост за этап ≥ 40k — правило нарушено, оформить работу в задание субагенту.

## Цикл этапа A<n>

0. Вход: main = origin/main = мерж предыдущего этапа, дерево чистое. `stage/A<n>.json` — копия предыдущего с правкой полей.
1. Запуск исполнителя — промпт 1 → `tools/book launch stage/A<n>.json --agent <agentId>` → конец хода.
2. Пришёл «ОТЧЁТ (этап A<n>)» → юзеру дословно (≤25 строк). PR не открыт — открыть одной командой по готовому телу исполнителя.
3. Механическая сверка: `tools/check stage/A<n>.json > /tmp/<slug>/A<n>.out 2>&1; tail -n 40 /tmp/<slug>/A<n>.out | cut -c1-200` → `problems = <число>`.
   - 0 → шаг 4; > 0 → самому не разбирать: следователь (промпт 3). Дефект скрипта — чинит он и повторяет; дефект PR — новый исполнитель на той же ветке, затем сверка заново.
4. `tools/book review stage/A<n>.json --text-file <файл со строкой ≤ 700 символов>` → агент закрытия (промпт 2) → `tools/book closing stage/A<n>.json --agent <agentId>` → конец хода.
5. Пришёл «ОТЧЁТ (этап A<n>) — закрытие» → юзеру дословно. «ВОПРОС (этап …)» → вывести юзеру; вслепую не повторять.
6. Подтверждающая сверка на main (`tools/check stage/A<n>.json --main`, вывод — в файл) → `tools/book close stage/A<n>.json` (PLAN: done; строка статуса; NOTES: `[orch]`) → `zctx --main --delta 20` → шаг 1 для A<n+1>.

## Промпты запуска (в Agent — только эти строки; остальное агент читает по путям)

1. **Исполнитель:** `Этап A<n> трека «<slug>»: прочитай <рана>/ORCH_PLAYBOOK.md, раздел «Роль: исполнитель», и сделай его шаги. Параметры: <рана>/stage/A<n>.json. Верни ≤25 строк, первая — «ОТЧЁТ (этап A<n>)».`
2. **Закрытие:** `Закрытие этапа A<n> трека «<slug>» после ревью оркестратора: прочитай <рана>/ORCH_PLAYBOOK.md, раздел «Роль: закрытие», и сделай его шаги. Верни ≤15 строк, первая — «ОТЧЁТ (этап A<n>) — закрытие».`
3. **Следователь:** `Следователь по ревью этапа A<n> трека «<slug>»: прочитай <рана>/ORCH_PLAYBOOK.md, раздел «Роль: следователь». Ввод: /tmp/<slug>/A<n>.out. Верни ≤30 строк: вердикт по каждой проблеме.`
4. **Инструментальщик** (один раз на трек, до A1): `Инструментальщик трека «<slug>»: прочитай <рана>/ORCH_PLAYBOOK.md, раздел «Роль: инструментальщик», и сделай его шаги. Верни ≤30 строк: команды и как их вызывать.`

## Роли (читает агент по пути из промпта запуска)

**Роль: исполнитель.** Прочитай: <путь к плану> целиком (исполняешь P<n>); `PLAN.md` раны — «Глобальный контекст» и «Контракты сабагента»; `NOTES.md`; `reports/A<n−1>.md` — только блок «⇒ Для следующего этапа». Шаги: (1) проверь состояние репо и ветку; (2) выполни этап, полный отчёт пиши в `reports/A<n>.md` по ходу работы, в конце — блок «⇒ Для следующего этапа»; (3) открой PR по заготовке <путь к шаблону PR>, без мержа. Вопрос — только блокирующий, по контракту: «ВОПРОС (этап A<n>)». Выводы команд — в файлы `/tmp/<slug>/A<n>/`.

**Роль: закрытие.** План и NOTES не читать. Шаги: (1) сверь вход — ветка, HEAD, PR = OPEN и MERGEABLE; расхождение — стоп, «ВОПРОС (этап A<n> — закрытие)»; (2) `gh pr merge <N> --merge`; (3) локальный main = origin/main, дерево чистое; (4) подтверждающий прогон `<команда>` — вывод в файл, ожидание `<условие>`; красный — не чинить: пауза ≥ 35 с и тот же прогон (до 2 повторов), снова красный — «ВОПРОС»; (5) допиши в `reports/A<n>.md` раздел «## После мержа» (блок «⇒» не трогать) и строку в NOTES с префиксом `[A<n>]`. `PLAN.md`, код, тесты и доки репо — не трогать.

**Роль: следователь.** Разбери каждую проблему из вывода сверки: (а) дефект скрипта — почини в `tools/`, self-тесты зелёные, повтори сверку; (б) дефект PR — не чинить, опиши точно (файл, строка, что не так, чем плохо); (в) не покрыто проверкой — предложи и добавь, если проверка механическая. Репозиторий — только чтение; `PLAN.md`, `NOTES.md`, `reports/A<n>.md` не трогать. Выводы — в `/tmp/<slug>/A<n>-invest/`.

**Роль: инструментальщик.** Напиши в `tools/` раны и опиши в `tools/README.md`: `book` (launch / review / closing / close — строки статусов PLAN.md, запись в NOTES, ротация NOTES при ≥ 40 КБ); `check` (механическая сверка этапа по `stage/A<n>.json`: гейты + правила ревью, итог — строка `problems = <число>`, артефакты — `reports/A<n>_artifacts/`); self-тесты. Оркестратору — только готовые команды, по одной на границу этапа.

## stage/A<n>.json — схема (общая для tools/check и tools/book)

```json
{
  "stage": "A<n>", "p": "<n>", "title": "<короткое название этапа>",
  "branch": "<ветка>", "base": "<merge-base, полный sha>", "head": "<PR HEAD, полный sha | null>", "pr": "<номер PR | null>",
  "plan": "<путь к плану>", "prTemplate": "<путь к заготовке PR>",
  "files": {"<путь к файлу>": "<роль файла в этапе>"},
  "gates": [{"name": "<имя>", "command": "<команда>", "expect": "<условие прохода>"}],
  "artifacts": "<рана>/reports/A<n>_artifacts",
  "expect": "<строка ожидания для PLAN>",
  "next_block": ["<N>", "<M>"]
}
```

`next_block` — номера строк блока «⇒ Для следующего этапа» в `reports/A<n>.md` (для промпта этапа A<n+1>).
