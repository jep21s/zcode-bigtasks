# zcode-bigtasks

Инструментарий для работы над большими задачами в ZCode: скиллы оркестрации
фоновых сабагентов, мониторинг заполнения их контекстного окна и бюджет
контекста самой сессии-оркестратора.

## Состав

| Компонент | В репо | Ставится в | Что делает |
|---|---|---|---|
| скилл **staged-task** | `skills/staged-task/` | `~/.agents/skills/staged-task` | Большая задача → конвейер этапов, по одному фоновому сабагенту на этап: план/отчёты на диске (`.staged/<slug>/`), маркеры «ОТЧЁТ»/«ВОПРОС», релей вопросов пользователя, пробуждение упавших агентов по id, экономия контекста оркестратора, контекстный бюджет оркестратора |
| скилл **track-task** | `skills/track-task/` | `~/.agents/skills/track-task` | Очень большая задача (трек) → фазы → этапы: playbook фаз (сабагент-архитектор), план фазы (сабагент-планировщик), конвейер этапов делегируется staged-task |
| **zctx** | `bin/zctx` | `~/.local/bin/zctx` | Замер заполнения контекстного окна сессии/сабагента по транскриптам `~/.zcode/cli/rollout/`: `zctx` — текущее заполнение, `zctx --main --delta 20` — рост окна основной сессии и его разбивка; база автомониторинга контекста из скиллов |
| шаблон **ORCH_PLAYBOOK.md** | `templates/` | — (читается из репозитория) | Заготовка runbook раны для длинных задач: правила, цикл этапа, промпты запуска, роли агентов, схема `stage/A<n>.json` |
| тесты zctx | `tests/` | — | `bash tests/test_zctx.sh` — 13 проверок на фикстурах `tests/fixtures/rollout/`; живой `~/.zcode` не трогается, rc = 0 ⇔ все прошли |

Связь компонентов:

```
track-task ──(этапный уровень)──▶ staged-task ──(мониторинг и бюджет контекста)──▶ zctx
```

track-task ссылается на staged-task по пути `~/.agents/skills/staged-task/SKILL.md`
(«каталог не переименовывать») — установка должна обеспечивать этот путь,
`install.sh` это делает.

## Установка

```bash
./install.sh          # симлинки (по умолчанию): репо — единственный источник истины
./install.sh --copy   # копии (для ФС без симлинков)
```

Требования: bash, `jq`, coreutils. Существующие файлы, отличающиеся
от репозитория, сохраняются в `.backups/` внутри репо. Пути назначения
переопределяются переменными `ZCODE_SKILLS_DIR` / `ZCODE_BIN_DIR`.

## Как обновлять

Правь файлы прямо в репозитории — симлинки подхватывают изменения мгновенно;
закоммить. На другой машине: `git pull && ./install.sh`.

После мержа PR, меняющего `skills/` или `bin/zctx`, достаточно обновить основное
рабочее дерево (`git pull`): симлинки указывают на него, скиллы и `zctx` обновляются
сразу. `./install.sh` нужен, только если симлинки сбиты или чего-то не хватает:
пересоздаёт их (в режиме `--copy` — заменяет копии скиллов и `zctx` на версии из репо;
отличающееся — в `.backups/`). `templates/` и `tests/` установкой не расходуются —
они читаются и запускаются из репозитория. При установке `--copy` шаблон runbook
на машине не появляется — берите его из репозитория.

Изменения в `bin/zctx` проверяйте тестами: `bash tests/test_zctx.sh`.

## Пороги мониторинга контекста (используются скиллами)

- окно сабагента — **500 000 токенов**, порог warn — **250 000 абсолютных**:
  `zctx -s <agentId> --limit 500000 --warn-at 250000` (проверка раз в 7 минут
  автоматикой CronCreate; warn/stop → кооперативная суммаризация и передача
  этапа новому агенту);
- основная сессия — лимит 1 000 000, warn 80%: `zctx --main` (дефолт без флагов берёт
  самый свежий файл — при работающем агенте это его файл);
- рост окна основной сессии — на границах этапов: `zctx --main --delta 20`
  (норма — ниже).

## Контекстный бюджет оркестратора

Правила скиллов запрещали читать исходники и требовали ревью по слайсам — но не
запрещали оркестратору писать код и выводить в контекст длинные результаты, и
ничего не мерили. Замер 24.11.2026 по транскрипту основной сессии (`.response.usage`):
**за 35 минут окно выросло 79k → 306k токенов**; из них ~183k — сумма `outputTokens`
модели (её рассуждения и тексты вызовов: скрипт ревью на 800 строк писался и ~10 раз
патчился прямо в основной сессии), ~44k — выводы инструментов.

Замер на границах этапов:

```bash
zctx --main --delta 20          # одна строка: рост, «свои ответы» / «инструменты и прочее»
zctx --json --main --delta 20   # поля deltaStart, delta, own, other, ownPct, requests
```

Норма (правила — в скиллах): «свои ответы» < 60% и рост за этап < 40k. Иначе работа
оформляется заданием субагенту (инструментальщик / следователь), а цикл ведётся по
runbook раны `ORCH_PLAYBOOK.md` (шаблон — `templates/ORCH_PLAYBOOK.md`).

Особенность живого каталога (наблюдение 24.11.2026): в `~/.zcode/cli/rollout/`
удерживались только 3 последних по времени записи транскрипта; более старые удаляются
и создаются заново при следующем запросе сессии. Поэтому, пока основная сессия ждёт
трёх и более параллельных сабагентов, `zctx --main` отвечает `main session not found`,
а после вытеснения `requests` показывает, сколько запросов реально попало в окно
(может быть меньше 20).
